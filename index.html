Android · llama.cpp · AGPL-3.0

Your spare Android phone, serving the OpenAI API.

Phonon runs llama.cpp on the phone and puts an OpenAI-compatible /v1 endpoint in front of it, behind an API key. Put LiteLLM in front of a few phones and your agent gets one URL. A Pixel 7 running Qwen3.5-2B holds 6.31 tokens a second for fifteen minutes without throttling.

The prompt is the expensive part.

Prefill on this phone runs at about 11–17 tokens a second. An agent's system prompt and tool schemas are a few thousand tokens before it reads your task, so the first turn is dominated by prompt processing. That's fine for a queue of work left running overnight, and painful if you're sitting there waiting.

The saving grace is the KV cache. llama-server keeps the prefix, so the first turn pays for the system prompt and later turns reuse it, as long as they land on the same phone.

What moved the number, and what didn't.

  • 50–60% fasterWeight repacking. llama.cpp is built with GGML_CPU_REPACK=ON at a revision that has Q4_K repack kernels. Without them, the same weights decode 50–60% slower. Decode here is limited by memory bandwidth, so the layout of the weights matters more than the core count.
  • ~1.4×Keeping the app on screen. The visible app gets the phone's two fastest cores; a backgrounded one doesn't. 7.59 against 5.36 tok/s in the same test.
  • 2.5 vs 9.0Speculative decoding with a 0.8B draft model. The draft reads its weights over the same memory bus, so it cost more than it saved. Not shipped.

Setup

The phone runs inference. Everything else happens on a host.

opencode (host)  ──▶  LiteLLM gateway  ──▶  phone-a:8080
                                       ──▶  phone-b:8080

Phone

One model, one slot, an OpenAI-compatible endpoint on the LAN. Runs as a foreground service so Android leaves it alone. It doesn't know about agents or sessions.

Gateway

LiteLLM, as configuration. One URL and one key for clients, one deployment per phone, plus routing, timeouts and metrics.

Worker

Your agent on a host. The repository uses opencode. It talks to the gateway, never to a phone directly. Anything that speaks the OpenAI API can use the same URL.

Two phones run two tasks at once, each at one phone's speed. Adding a phone adds a worker. It doesn't make anything faster.

Pin agents to a phone.

Round-robin throws away the cached prompt prefix on every turn. The gateway template exposes pinned names (phone-a, phone-b) for agent work and one pooled name for one-shot calls.

Change LiteLLM's defaults.

They assume cloud latency, and a phone can take minutes to reach the first token. The template sets 1,800-second timeouts and zero retries, because a retry pays for the whole prompt again.

opencode has run a file task end to end through the gateway on one phone, using an agent cut down to four tools (bash, edit, read, write). That costs about 2.8K tokens, which leaves roughly 5K of an 8K window for the actual work.

The app

What the app does around the model.

Supervises llama-server

If the server exits unexpectedly, the app restarts it, waiting 1 s and doubling up to 30 s. Killed with kill -9 on the Pixel, it was serving again in 4 s under a new pid.

One port, always answering

The app listens on 8080 and proxies /v1 to llama-server on an internal port. /health still answers while the model is loading, restarting or paused.

No key, no LAN

It binds to 127.0.0.1 by default. Any other address requires an API key. Without one, the server won't start on that address and the app tells you why.

Checks what it downloads

Resumes interrupted downloads and checks the size and SHA-256 against the catalog. A file that doesn't match is deleted. It won't start a download the disk can't hold, and it asks before fetching a model too big for the phone's RAM.

Backs off when hot

Reads the battery temperature every 30 s. By default it stops the server at 45 °C and restarts it at 40 °C. Both thresholds are settings.

Measures itself

Runs a benchmark on the device and exports a device report you can share. A particle avatar shows the server's state; at full animation it costs about 2.4% of decode, so full animation is off by default.

While it serves, the app keeps the screen on: the visible app gets the phone's fastest cores, and a backgrounded one does not. It can also lock itself into kiosk mode when it is the phone's Device Owner.

Models

Eight models from five families. The tested ones have numbers.

The app downloads GGUF files from pinned Hugging Face URLs. On first start it picks a model for the phone's RAM (Qwen3.5-2B on the Pixel 7) and never overrides your choice after that. Every family returned structured tool_calls on the phone.

Limits

What it won't do, and what isn't tested.

  • One model per phone at a time.The whole model runs on one phone. This is not distributed inference, and phones don't share a model.
  • One request in flight per phone.The server runs a single slot. If you want more concurrency, add phones.
  • Only the Pixel 7 has been measured.Other phones need measuring before anyone quotes numbers for them: one manifest per device, filled in by the repository's benchmark script. A device PR without measured numbers isn't accepted.
  • Kiosk mode needs Device Owner.Android only allows that on a phone with no accounts on it. The reference Pixel had accounts, so every number on this page was taken without kiosk mode.
  • The app can't control charging.Android doesn't let an ordinary app touch the charger. Phones stay plugged in, so turn on the Pixel's Charging optimization with the 80% limit.
  • No TLS on the LAN.Traffic is plain HTTP and the API key goes over the network in clear text. Use it on a network you trust. Don't port-forward it; for remote access, put WireGuard, Tailscale or an SSH tunnel in front.
  • Tested over USB, not yet over Wi-Fi.Every measurement so far went over adb forward. A second machine reaching the phone over Wi-Fi or Ethernet hasn't been tested end to end.
  • No telemetry.The only outbound connection the app makes is a model download, from the catalog's Hugging Face URL or one you give it. A device report leaves the phone only if you share it.

Getting it

Build it yourself. There's no download yet.

No release has been tagged, so there is no APK. Packaged builds for GitHub Releases and F-Droid are being prepared. The app builds from source, including llama.cpp, which comes from a pinned submodule. No prebuilt binaries are committed.

  1. Check what you need

    An arm64 Android phone on Android 12 or later, with 8 GB of RAM for the default model. On the build machine: JDK 17, Android SDK platform 35, and NDK 30.0.16138531, the version the published numbers were built with.

  2. Build

    git clone --recursive https://github.com/chezgoulet/phonon
cd phonon
export ANDROID_NDK_HOME=$ANDROID_SDK_ROOT/ndk/30.0.16138531
./app/build-native.sh
./app/gradlew -p app :app:assembleDebug

    Details, and what F-Droid's build server needs, are in BUILDING.md.

  3. Serve

    Install the APK, pick a model, and set an API key before you bind to a LAN address. Leave the phone on USB power, in open air, with no case. Then point a client or a LiteLLM gateway at http://<phone>:8080/v1. A two-phone gateway config is in gateway/.
